# Registro de Deuda Técnica y Mejoras Futuras

Este documento mantiene un registro de los atajos técnicos tomados durante el desarrollo del MVP para mantener la velocidad, así como problemas conocidos y casos borde que no bloquean el uso principal de la aplicación.

## 🔴 Alta Prioridad (Requerido antes de lanzar a clientes reales)

- **[Seguridad] Tests de Integración E2E para RLS:** Actualmente el aislamiento multi-tenant (la Barbería A no puede ver datos de la Barbería B) está probado manualmente en el navegador. Se necesita montar un entorno de base de datos de test automatizado para verificar que ninguna política RLS se rompa por accidente en el futuro. Incluye `cash_sessions` (spec 04): el bloqueo de doble caja (índice único), el aislamiento entre barberos de una misma barbería y el aislamiento entre barberías se probaron a mano con scripts descartables (`@supabase/supabase-js` + service role/anon key) contra el proyecto real, no con un test automatizado que corra en CI. `appointments`/`transactions` (spec 05) heredan el mismo hueco: el flujo feliz (crear servicio, abrir caja, iniciar/finalizar timer, cobrar) se probó de punta a punta en el navegador contra el proyecto real, incluyendo verificar el `appointment` y la `transaction` resultantes directo contra la base, pero el aislamiento entre barberos/barberías de estas dos tablas nuevas no se probó a mano (a diferencia de `cash_sessions` en la spec 04) — se asumió por heredar el mismo patrón de policies ya verificado ahí.
- **[Transaccionalidad] `completeWalkinAction` sin RPC atómico:** son dos inserts separados (`appointments`, después `transactions`) porque no hay Postgres RPC para esto (ver `docs/decisiones.md` — mover lógica a Server Actions en vez de RPC/triggers es la decisión de arquitectura vigente). Si el insert de `appointments` se guarda pero el de `transactions` falla, el corte queda registrado sin reflejarse en la caja: el Server Action devuelve un error explícito pidiendo revisar el desfase a mano, pero no hay compensación automática (ni un job que reconcilie) todavía.
- **[Caja] `closeCashSessionAction` no suma las `transactions` al cerrar caja:** desde la spec 04, `final_balance` se calcula como `final_balance = initial_balance` (`cash.actions.ts`) — en ese momento era correcto porque no existían cobros. Desde la spec 05, `completeWalkinAction` sí genera filas en `transactions` (`type: "income"`) por cada corte cobrado, pero `closeCashSessionAction` nunca se actualizó para sumarlas: hoy un barbero puede cobrar varios cortes durante el día y, al cerrar caja, el `final_balance` guardado va a seguir siendo igual al saldo inicial, sin reflejar lo cobrado. Las `transactions` individuales sí quedan bien guardadas en la base (verificable a mano), el problema es solo el cálculo de `final_balance` al cerrar. Hay que sumar `SUM(transactions.amount WHERE type='income') - SUM(... WHERE type='expense')` (vía la `cash_session_id` de la caja) antes de guardar el cierre.

## 🟡 Media Prioridad (Estabilidad y Mantenibilidad)

- **[Testing] Tests automatizados de UI interactiva:** Componentes complejos del cliente como `ServiceList.tsx`, el `Switch` optimista, `ServiceInlineForm.tsx`, `OpenCashView.tsx` y `CloseCashButton.tsx` (spec 04) no tienen cobertura de Testing Library. Si cambian, corremos el riesgo de introducir regresiones visuales o de interacción. `OpenCashView.tsx` es el caso más delicado: `handleAmountChange` maneja a mano la posición del cursor al reformatear el monto con separador de miles (ver `docs/decisiones.md` 2026-09-15) — es la lógica de UI más propensa a romperse silenciosamente sin un test que la cubra. `TimerList.tsx`, `TimerCard.tsx` y `FinishWalkinForm.tsx` (spec 05) suman a esta misma deuda: el `setInterval` de `TimerCard` y la rehidratación de `persist` (`useTimerStoreHydrated`) tampoco tienen tests — se probaron a mano en el navegador (incluyendo F5 con un timer corriendo), no con Testing Library/fake timers.

## 🟢 Baja Prioridad (UX y Casos Borde)

- **[Catálogo] Race condition en UI Optimista:** Si se hace doble tap muy rápido en el switch de activar/desactivar servicio con una red lenta, el estado optimista podría desfasarse momentáneamente del servidor. Se corrige solo al refrescar la página.
- **[Catálogo] Acumulación de servicios inactivos:** La lista de servicios actualmente renderiza todos los elementos. A largo plazo, los servicios inactivos/antiguos crecerán y harán la lista muy larga. Falta implementar paginación o un filtro para ocultar los inactivos.
- **[Caja] Sin tope de dígitos en el saldo inicial:** `OpenCashView.tsx` (spec 04) achica la letra a medida que se escriben más dígitos, pero no hay un `maxLength` ni una validación de "monto irreal" — un saldo inicial de más de ~12 dígitos (imposible en la práctica) se ve apretado. No bloquea el uso real de una caja diaria.
- **[Equipo] Inconsistencias menores en `/equipo` (revisadas 2026-09-15, sin aplicar todavía):** (1) el botón "Agregar Barbero" está en Title Case, el resto de la app usa oración normal ("Nuevo servicio", "Iniciar corte"); (2) el campo de mail en `BarberInlineForm.tsx` dice "Correo", pero login/registro usan "Email" para el mismo dato; (3) el dueño aparece en la lista con "0%" de comisión al lado de "Dueño" — un dueño no cobra comisión, ese número no tiene significado para ese rol y puede leerse como un dato roto; (4) el error de `equipo/page.tsx` usa `text-red-600` crudo de Tailwind en vez del token `text-danger`. No bloquea el uso de la pantalla.
